# 开源技能方法论吸收

把别人的技能"吸收"进自己的技能时，**最大的风险不是技术，是设计**——挂错位置会让主文件变胖，硬合并会让触发词污染。

## 铁律（违反任何一条都要重做）

### 铁律一：模块只能挂"可选支线"，不能挂"必经路径"

这是最容易犯的错。判断方法：

**列出目标技能的所有阶段，标出哪些是"每次都会经过"、哪些是"满足条件才进"。**

- 挂在必经路径的模块 = 伪懒加载，它会变成常驻负担
- 只有挂在可选支线，才是真懒加载

**反例（真实踩坑）**：把"戏剧引擎"模块挂在「阶段二/三」——但这两阶段是每条脚本必经，结果 4KB 文件变成每次必读。
**正解**：把精华压成 3-5 行直接写进主文件（每题必过的东西就该内嵌），大段细节才做成可选支线模块。

**决策规则**：
- 「每题必过」的内容 → 压缩后内嵌主文件
- 「满足条件才用」的内容 → 独立 modules，挂可选支线
- 「历史文档」（更新日志、版本记录）→ 一律外置，不常驻

### 铁律二：硬合并前先查三个冲突

| 冲突类型 | 检查方法 | 后果 |
|---------|---------|------|
| **触发词污染** | 把两个技能的 description 触发词摆在一起看，有没有场景重叠/包含关系 | 用户说 A 场景被路由到 B 流程 |
| **交付物冲突** | 两个技能最终产出什么？形态是否互斥（如 文档 vs 代码、实拍表 vs AI提示词） | 硬合并后指令互相打架 |
| **上下文预算** | 两边总体积相加，对比目标技能当前体积 | 主文件爆炸，触发质量下降 |

**任一冲突成立 → 放弃"合成一个"，改用"能力吸收 + 独立并存"。**

### 铁律三：主文件体积预算

**主文件是每次对话都读的，它有预算。**

- 记下改动前的字节数，明确写下一个上限（如"不超过 32KB"）
- 优先外置：更新日志、案例库、长表格、历史版本记录
- 改完必须实测，**超预算就外置其他内容去抵消**，不要假装没超

### 铁律四：备份（⚠️ 2026-09-30 用户已废止，默认跳过）

**用户明确要求：删除/合并就干净利落，不做备份、不留后悔药。** 默认跳过备份步骤，直接动手。

仅当用户主动说「先备份一下」时才备份。备份时注意：`~/.workbuddy/skills/` 下的子目录只要含 SKILL.md 就会被扫描成重复技能，所以备份必须放技能目录之外，备份后验 MD5 一致再动手。

### 铁律五：写完必须统一换行符

**Windows 上 Python 文本模式写入会把 `\n` 转成 `\r\n`。**

原文如果是 LF，改写后就变成 CRLF，字节数虚增（每行 +1），可能误判"超预算"。

验证与修复（处理完后跑一遍）：
```python
import glob
base = r'C:/Users/Administrator/.workbuddy/skills/<技能名>'
for p in sorted(glob.glob(base + '/**/*.md', recursive=True)):
    b = open(p, 'rb').read()
    crlf = b.count(b'\r\n'); lf = b.count(b'\n') - crlf
    print(p, len(b), 'CRLF' if crlf and not lf else ('LF' if lf and not crlf else '混合'))
```
需要统一时：`open(p,'wb').write(b.replace(b'\r\n', b'\n'))`

## 标准流程

### 第一步：拿到源技能

GitHub 直连在国内通常不通。用镜像：
```bash
git clone --depth 1 https://ghfast.top/https://github.com/<用户>/<仓库>.git
# 备用镜像：https://gh-proxy.com/https://github.com/...
```

`.skill` 文件实为 zip，解压可见内部结构：
```python
import zipfile
zipfile.ZipFile(r'xxx.skill').extractall('解压版')
```

### 第二步：全量通读，不要抽样

**必须逐字读完源技能和目标技能的全部文件。** 抽样会漏掉关键设计（如某个模块其实挂在必经路径上）。

读完后做三张清单：
1. **重叠区**：两边都在做的事（可择优统一）
2. **互补区**：一方有另一方没有的（合并的价值所在）
3. **冲突区**：不能硬合的理由（见铁律二）

### 第三步：出方案并让用户选

给三个方案 + 明确推荐：
- 方案 A：能力吸收 + 独立并存（通常最优）
- 方案 B：深度合并成一个（通常不推荐）
- 方案 C：技能族 + 总控路由（中期演进）

### 第四步：按铁律执行

1. 内嵌「每题必过」的少量内容到主文件
2. 新建可选支线模块
3. 改路由指令、版本号、来源署名
4. 外置历史文档（如果超预算）
5. 统一换行符（铁律五）

（备份步骤已废止——见铁律四，仅用户主动要求时才做）

### 第五步：交付前验证清单（逐项实测，不靠感觉）

| 检查项 | 命令/方法 |
|--------|----------|
| 文件清单与换行符 | Python 遍历，确认全部 LF |
| 主文件体积 | 对比预算，明确是否达标 |
| frontmatter 字段 | 确认 name/slug/version/description 等齐全 |
| 新增内容就位 | grep 每个关键锚点，确认出现次数 |
| 代码块配对 | `grep -c '^\`\`\`'` 应为偶数 |
| 原有内容未丢 | grep 所有原章节标题 |

**发现超预算或有瑕疵时，如实告诉用户并修掉，不要隐瞒。**

## 许可与署名

吸收开源内容前先看协议。常见 MIT 协议要求：
- 可自由使用、修改、二次分发
- **必须保留原作者署名**
- 禁止二次售卖技能本身

在目标技能的「来源」章节和吸收处标注原作者，例如：`方法论源自 @XXX（MIT 协议）`。

## 关键教训速查

1. 模块挂错位置 = 伪懒加载，必须挂可选支线
2. 三冲突（触发词/交付物/上下文）任一成立就不能硬合并
3. 默认不备份（用户 2026-09-30 明确）；仅用户主动要求时才备份，且备份不能放 skills/ 目录内，会被扫描成重复技能
4. Windows Python 写入会改 CRLF，必须显式统一
5. 历史日志外置是给主文件腾空间最快的手段
6. 交付前逐项实测，不靠"应该没问题"
